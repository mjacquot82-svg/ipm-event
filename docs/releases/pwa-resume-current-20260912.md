# Staging resume updater A/B candidate

Production verified at e93ead504d8734a0b35abce97bce59a36988d572, deploy 6aa5b1c9cc9a8300082e8643. Canonical staging base: 7ca9ee603e98ac4d496f64e16be0b9c0a743f210.

The new branch starts from remote staging, preserving its independent backend, notification, configuration, and schedule changes. Before updater work, it selectively ports the approved production vendor-runtime fix (fe40a994) and generic unmapped UX (e93ead50). No catalog or geometry changes. The vendor cache conflict retains staging event-media types and uses the approved canonical web cache. This staging branch must NOT be wholesale merged to production.

PR14 (bd42d605) is reference only. Reused concepts: ten-minute background threshold, explicit Refresh/Later, notification/install holds, activation message. Reworked: no 45-second scheduler/startup prompt; tiny generated entry manifest instead of downloading HTML to detect updates; persistent per-tab one-shot guard; bounded requests; canceled refresh when hidden/unsafe; no unsolicited controllerchange reload. Staging's existing shared current-v1 last-known-good cache stays unchanged, preventing activation from deleting currentLaunch's concurrent cache. currentLaunch itself is unchanged. Production currently has a different versioned-cache installation policy; future production promotion needs a fresh cache-lineage review.

Decision: Refresh/Later, on Home only. Automatic re-entry refresh cannot guarantee a safe boundary once the asynchronous check finishes. Detection may occur after a qualifying resume on any route, but presentation waits for Home, visible/online state and no notification/install holds. Later suppresses the target until the next qualifying background. Only a Refresh tap revalidates the release and requests a worker update, waits for installation, then explicitly activates a waiting worker; controllerchange reloads once. If no waiting worker exists, currentLaunch fetches the new shell on explicit reload. Timeout, offline, failed probe or unavailable session storage leaves the app running. No retry polling. A canceled activation never causes a delayed reload when Home becomes safe later.

The probe is /app-release.json with a cache-busting query and no-store; it contains only the emitted entry path and is not in the offline cache. Persisted session target prevents repeated reloads even if a navigation falls back to the old shell. It does not clear application storage or touch permissions/subscriptions. A fresh tab may attempt an update again. Cross-tab updates never cause unsolicited page reloads.

WonderPush source, bootstrap, web-key handling, subscription code, push/click ownership and root registration remain identical to staging base. Only a conditional explicit worker activation handler is added. No provider calls are part of browser fixtures: the local two-generation test stubs the SDK and checks browser storage and Notification.permission; actual provider installation continuity requires the Android check. No provider configuration or production data is changed.
