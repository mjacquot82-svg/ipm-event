7. **Actual production PWA lifecycle.**
   - On a full web application startup, root layout calls `initializeOfflineShell()` independently of notification permission. It registers `/webpushr-sw.js?webKey=…` at scope `/`, with `updateViaCache: 'none'`. It explicitly calls `registration.update()` when online and installs an `online` listener that checks the root registration again. The promise is cached per loaded JavaScript document. Production has no IPM foreground/focus/visibility polling, waiting-worker listener, update notice, controller-change reload, or explicit activation-message handler.
   - The build generator hashes the shell asset paths/content, including HTML, to a 16-character SHA-256-derived version. Each build precaches `/`, `/index.html`, the hashed entry JavaScript, essential fonts/images/icons and manifest into `ipm-offline-shell-<version>` with one `cache.addAll()` installation promise. A failed required fetch can prevent installation; a partial/new cache is not proof that a worker has activated.
   - The worker imports WonderPush's loader. At audit time it resolved to SDK **1.1.44.0**. The imported SDK's install handler calls `skipWaiting()` after its instantiation promise resolves, and its activation handler claims clients. This is conditional on successful provider initialization; IPM's own worker does not call `skipWaiting()`.
   - If that provider lifecycle runs, the new worker can activate while an old page remains open. IPM activation removes prior `ipm-offline-shell-*` caches and calls `clients.claim()`. Claiming a page does **not** replace already executing JavaScript. The attendee sees N until a full navigation/reload creates a document from the new shell.
   - If provider initialization cannot complete, the standard waiting path remains: install N+1 → wait while an N-controlled client exists → close all such clients → activate → next navigation receives N+1. Closing only one of several controlled windows may be insufficient.
   - Every controlled HTML navigation, including Admin and deep links, returns the active worker's cached `/index.html` first. It only fetches the navigation if that HTML is absent. Recognized shell JS/CSS/assets are cache-first with query strings ignored. Other same-origin resources fall through to the network; `/api/` requests and cross-origin requests are not cached by this shell handler. There is no IPM stale-while-revalidate HTML or asset strategy and no separate Workbox lifecycle.
   - Observed Netlify HTML, worker and hashed-JS HTTP headers were `Cache-Control: public,max-age=0,must-revalidate`, with ETags; the worker registration additionally bypasses the browser HTTP cache for update checks/imports. These headers do not bypass an already controlling service worker's Cache Storage response.
   - **Deployment while closed:** the first reopen can be served N by the old active worker; startup then discovers/downloads N+1. If activation finishes after that document loaded, another full navigation/reopen is needed to run N+1. **Open through deployment:** loaded JS remains N; there is no application-level notice. **Suspended installed app:** returning to its icon may resume the same document, without rerunning startup. **Offline:** N remains usable; reconnect checks for an update but does not replace the running document. **Deep links:** retain their URL while the shell is served, then Expo Router resolves the route.
   - Staging already had a separate update scheduler/activation/reload implementation and an Admin recovery path. Those were preserved on staging and were **not** promoted to production.
